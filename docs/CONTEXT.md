## 0. Ключевое правило: игра многопользовательская

**Zorion — это игра с одновременной работой нескольких игроков на одном сервере.**
Об этом надо помнить при **любой** правке кода. Нагрузка одного игрока — не показатель,
проблемы начинаются, когда двое (или больше) делают что-то одновременно.

### Что это значит на практике

- **Любая map, к которой могут обратиться две горутины — должна быть защищена мьютексом.**
  Go убивает процесс при `concurrent map writes`, никакой `recover` не спасает.
- **Любой синглтон** (`sync.Once` в `getPlanetGenerator`, глобальный `statusManager`,
  `WebSocketHub`, `TravelManager`) — потенциальный источник гонок.
- **Общие рандомы** (`*rand.Rand` на уровне пакета) не потокобезопасны. Или мьютекс,
  или локальный `rand.New(...)` на каждый вызов.
- **Сторонние библиотеки** могут быть не потокобезопасны (gorilla/websocket — только
  одна горутина на запись в соединение).
- **Проверка + действие** должны быть атомарными (`TryStart` вместо `if running + Start`).
- **Долгие операции** (генерация, bcrypt) увеличивают окно гонки — не полагаться
  на «успею проверить до следующего запроса».

### Что уже защищено

| Компонент | Защита |
|-----------|--------|
| `PlanetGenerator.cache/cacheOrder/rand` | `sync.Mutex` |
| `WebSocketHub.clients` + запись в conn | Глобальный `RWMutex` + per-connection мьютекс |
| `TravelManager.flights` | `RWMutex` + проверка `current == flight` |
| `StatusManager.jobs` | `RWMutex` + `TryStart` (атомарно) |
| `CompatibilityMatrix` (кеш) | `RWMutex` |
| `archetypeCache`, `jwtSecret` | Только чтение после инициализации |
| `*sql.DB` (везде) | Потокобезопасен «из коробки» |

### Что ещё не защищено (известные долги)

- `Register` в `auth_handlers.go` — race между `GetByUsername` и `Create`
  (БД защищает через `UNIQUE`, но возвращается 500 вместо 409).
- `planet_image.go` — кэш пишется, но не читается. Когда добавим чтение —
  обязательно под мьютексом.
- **Кеш аномалий** (когда появится Go-код для чтения `config/anomalies/`) —
  под `RWMutex`, только чтение после инициализации. Загружать один раз при старте,
  при ошибке чтения JSON — валить сервер явно (`log.Fatal`), а не стартовать
  с полупустым кешем.
- **Не проверено:** `internal/generator/faction/faction.go`,
  `internal/generator/galaxy/galaxy.go` (при параллельной генерации).

### Как проверять при разработке

- Перед мержем **любой** правки, где появляется `var x = map[...]` на уровне пакета —
  спросить: «а если два игрока одновременно?».
- Перед мержем **любой** правки с `go func()` — подумать о разделяемом состоянии.
- Раз в N задач — перечитывать `go vet -race` (когда появится CI).
- При первом баге «сервер упал у игрока» — в первую очередь смотреть на map и горутины.

## 2. Что сделано в последних сессиях

### 2.1. Аудит планет

- Пакет `internal/audit` — дженерик-движок `Run[T]`, расширяемо на другие сущности.
- Подпакет `internal/audit/planet` — **43 правила** проверки планет.
- HTTP-хендлер `GET /admin/audit`.
- Вкладка «🔍 Аудит» в админке с фильтрацией и примерами.

### 2.2. Карточка планеты

- Модалка разбита на `tabs.js` + `panel.js` + `index.js`.
- Показывает: массу, размер, плотность, температуру, ядро, композиции поверхности и недр, спутники.
- Цветная полоска + иконки для композиций.
- Обрезка топ-7 форм с кнопкой «показать все».

### 2.3. Фикс гонок конкурентности

| Файл | Что было | Что стало |
|------|----------|-----------|
| `planet_image.go` | `concurrent map writes` → падение сервера | `sync.Mutex` на `cache`/`cacheOrder`/`rand` |
| `websocket_hub.go` | Параллельная запись в соединение | `wsClient` с per-connection мьютексом |
| `travel/manager.go` | Старый полёт удалял новый | Проверка `current == flight` |
| `status.go` | Неатомарная проверка + старт | `TryStart` |
| `admin_universe.go` | `r.(string)` в recover → паника | `recoverErr` |
| `admin_universe.go` | `ClearUniverse` при генерации | 409 Conflict |

### 2.4. Балансировка биосферы

- При `T < 250 K` биосферные формы ×0.05 (было ×0.2–0.3).
- Абсолютные запреты: лава при `T < 500`, лёд при `T > 320`.
- Спутники не горячее гиганта (`tidal` снижен с 400 до 100 + потолок).
- **Результат аудита:** 4702 → 1364 → ожидаем ~50–100 (после перегенерации).

### 2.5. Обсуждения в GDD

- **Аномалии как контент** — редкие «нарушения» физики как фича, с художественными описаниями.
- **LLM-генерация описаний** — при создании планеты → сохранение в БД.
- **JWT-секрет** — критично: сейчас хардкод, надо в env.

### 2.6. Библиотека аномалий — готова

**Что сделано:**

- Папка `config/anomalies/` — **22 JSON-файла**, по одному на аномалию.
- Формат: `code`, `title`, `icon`, `seeds` (10 × 2 абзаца), `tails` (10 × 1 абзац).
- Композиция текста: `seed + "\n\n" + tail` = 3 абзаца, ~150–200 слов.
- Детерминированный выбор по хэшу:
  - `seedIndex = hash(planet.id + code + ":seed") % 10`
  - `tailIndex = hash(planet.id + code + ":tail") % 10`
- До 100 вариантов текста на аномалию, до 2200 комбинаций на всю библиотеку.
- `config/anomalies/README.md` — описание формата.
- Коды совпадают с кодами правил в `internal/audit/planet/`.

**Состав библиотеки (22):**

Физика и климат:
`glaciers_in_heat`, `lava_in_cold`, `oceans_in_heat`, `oceans_without_water`,
`greenhouse_in_cold`, `methane_in_heat`, `oxygen_in_heat`, `hydrogen_in_heat`,
`radioactive_without_zones`.

Биология и экосистемы:
`jungles_in_cold`, `forests_in_cold`, `meadows_in_cold`, `swamps_in_cold`,
`coral_reefs_in_cold`, `biosphere_without_water`, `life_without_water`,
`life_without_temperature`, `habitable_without_life`.

Спутники и системы:
`satellite_hotter_than_giant`, `satellite_mass_too_high`.

Население:
`population_without_habitable`, `population_on_gas_giant`.

**Отдельно:** 7 файлов (`greenhouse_in_cold`, `habitable_without_life`,
`methane_in_heat`, `oceans_without_water`, `oxygen_in_heat`,
`population_on_gas_giant`, `satellite_mass_too_high`) были написаны другой
моделью и содержали языковые вставки (китайские/английские обрывки).
**Переписаны с нуля** в едином стиле.

**Что осталось (Go + фронт):**

- Go-код: чтение `config/anomalies/` при старте, кеш в памяти под `RWMutex`.
- API: эндпоинт, отдающий тексты фронту.
- Детекция на фронте по данным планеты (по кодам из аудита).
- Показ: отдельный блок в карточке планеты, внизу под описанием.

## 9. Как обновлять этот файл

В конце каждой сессии:

1. Обновить дату сверху.
2. Перенести завершённое из «что дальше» в «что сделано».
3. Переписать раздел 1 («текущий фокус»).
4. Добавить новые открытые вопросы, убрать решённые.
5. Ничего не удалять из раздела 2 — это лог решений.
6. **Раздел 0 (многопользовательская архитектура)** — обновлять при каждом новом
   найденном или починенном конфликте. Это ключевое правило проекта.
