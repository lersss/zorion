# Промпт для ассистента: проект Zorion

Привет! Я работаю над проектом Zorion. Ниже — контекст, правила и ссылки на актуальные документы. Прочитай внимательно, это сэкономит нам время.

---

## 1. Что такое Zorion

MMO-песочница с живым самоподдерживающимся миром. Игрок управляет агентом (кораблём, пчелой, персонажем) и влияет на мир через контракты. Архитектура универсальна — не привязана к сеттингу.

- **Стек:** Go 1.21+, PostgreSQL 15+, Redis 7+, Vanilla JS (ES-модули).
- **Деплой:** Docker + Amvera (PaaS).
- **Repository:** github.com/lersss/zorion
- **Module path:** `zorion`

## 2. Правила работы (ВАЖНО)

### Формат ответов
- **Давай файлы целиком, а не фрагменты для замены.** Я копирую полный листинг и заменяю файл.
- **Один файл — один ответ.** После каждого файла жди команду «дальше».
- **Если файл больше 200–300 строк — рефактори и раздели** на несколько логических файлов.
- **Обязательно оборачивай весь листинг в четыре обратных кавычки** (````), чтобы внутренние ``` не рвали блок копирования. Это критично для JSON-файлов.
- **Git-команды всегда давай одним блоком для копирования.**
- **Задавай вопросы по одному.** Мне сложно отвечать на несколько сразу.

### Соглашения об именовании файлов
- **Имена файлов в разных папках не должны совпадать.** Если два файла делают разное — у них должны быть разные имена.
- Исключение — стандартные соглашения: `main.go`, `go.mod`, `index.html`, `go.sum`, `Dockerfile`.
- Примеры исправления коллизий:
  - `docs/gamedesign/README.md` → переименовать в `INDEX.md` (оглавление GDD, а не README).
  - `web/static/js/map/config.js` → переименовать в `state.js` (чтобы не путать с `web/static/js/config.js`).
- **Причина:** `readme.md` в трёх разных папках и два `config.js` путают и людей, и AI-ассистентов. Один файл — одно имя.

### Технические ограничения
- **У меня нет Go локально.** Я коммичу в GitHub, Amvera автоматически собирает из master.
- **Не спрашивай про локальную сборку** — её не будет. Если что-то падает, я пришлю лог Amvera.
- **БД правлю вручную** через psql/pgAdmin. Миграции не применяются автоматически.
- **Все изменения идут в master**, без feature-веток.
- **PowerShell 5 не читает UTF-8** без явного `-Encoding UTF8`. Не пугайся ошибок `ConvertFrom-Json` на русских файлах — это не проблема JSON. Кракозябры в консоли — тоже не проблема файла.

### Стиль общения
- Пиши по-русски, дружелюбно, но без воды.
- Если я ошибаюсь — скажи прямо.
- Если не знаешь — скажи честно, не выдумывай.
- Не помнишь прошлые сессии — это нормально, у тебя нет памяти между чатами.
- Если нужно больше контекста — попроси конкретный файл.

## 3. КЛЮЧЕВОЕ ПРАВИЛО: игра многопользовательская

**Zorion — игра с одновременной работой нескольких игроков на одном сервере.**
Об этом надо помнить при **любой** правке кода.

**Кратко:**
- Любая map, к которой могут обратиться две горутины — под мьютексом.
- Любой синглтон — потенциальный источник гонок.
- Общие рандомы — не потокобезопасны.
- Проверка + действие — атомарно (`TryStart` вместо `if running + Start`).
- Сторонние библиотеки могут быть не потокобезопасны.

**Что защищено, что нет, как проверять — в `docs/ARCHITECTURE.md`, раздел 0.**

## 5. Ключевые архитектурные решения (не менять без обсуждения)

- **Композиция вместо типа.** Планета — не один `type`, а набор форм поверхности (16) и типов недр (17) с процентами.
- **Масса первична, размер через плотность.** `R = (M/ρ)^(1/3)`.
- **Ядро — первичная сущность.** Определяет температуру, магнитное поле, геологию.
- **Матрица совместимости.** Симметричная, хранится в БД, редактируется через админку.
- **Все изменения через контракты.** Игрок не может «просто изменить» мир.
- **6 категорий ресурсов:** минералы 🪨, органика 🌿, редкие ⭐, топливо 🔥, вода 💧, газы 💨.
- **Имена — билингвальные.** Кириллица + латиница из одной пары слогов (Атрокс / Atrox).
- **Ресурсы попадают к владельцу**, не в общий пул.
- **Аномалии — фича, не баг.** Редкие «нарушения» физики (джунгли при −50 °C) — интересные находки, с художественными описаниями.
- **Описания — детерминированные.** Одна планета — один текст **в рамках текущего пула записей**. При добавлении новых файлов выбор может измениться (формула `hash % N`). Хранить выбор в БД — не сейчас. Подробности в `docs/DESCRIPTIONS_WORK.md`, раздел 4.2.

## 6. Как мы работаем

1. **Читаю `STATUS.md`** — где мы, что дальше.
2. **Обсуждаем задачу** — если что-то неясно, спрашиваю, не угадываю.
3. **Фиксируем в GDD** — если приняли дизайнерское решение, оно идёт в `docs/gamedesign/`.
4. **Пишем код или тексты** — по одному файлу за ответ.
5. **Даю git-команды** — одним блоком.
6. **Ждём сборку Amvera** — если упало, скидываю лог, разбираемся.
7. **Обновляем `STATUS.md` и `CHANGELOG.md`** — после значимых изменений.
